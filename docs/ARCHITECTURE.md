# Контракты MVP-2

## Поле и кодирование

`cells[y * width + x]`, координаты `[x,y]`, начало слева сверху. Временная пустота — `null`. Обычные фишки сохранили номера MVP-1. Полный код — `kind * 16 + color`: normal=0, rocket-h=1, rocket-v=2, bomb=3, lightning=4. Используйте `makeTile`, `tileKind`, `tileColor`, `isValidTile`, а не числовые смещения в приложении.

Ракеты/бомбы участвуют в matches по базовому типу; молния не участвует. MatchFinder выдаёт максимальные горизонтальные и вертикальные линии. SpecialFactory объединяет пересекающиеся линии, выбирает тип и точку создания. Независимые группы обрабатываются независимо.

Геометрия core по-прежнему прямоугольная. Дыры, препятствия и ограничения перемещения появятся на MVP-4. Стенд показывает только 8×8; интерфейс более сложных полей не реализован.

## Приоритеты создания

Один special на связанную группу: линия 5+ → молния; T/L → бомба; линия 4 → ракета направления линии. Якорь выбирается из обычных фишек группы: сначала клетка назначения хода, затем исходная клетка, пересечения, наименьший индекс. В каскадах приоритет клеток последнего ручного swap не применяется. Existing specials не перезаписываются. Если в группе нет обычного кандидата, нового special не создаётся.

Якорь исключается из списка удаления этой волны и не активируется взрывом в той же волне. Новая фишка может упасть, а в следующих каскадах срабатывает обычным образом.

## Срабатывание

SpecialResolver вычисляет геометрию до удаления. Очередь обходится в фиксированном порядке; повторные попадания дедуплицируются. Каждый существующий special активируется максимум один раз за волну. При попадании в молнию взрывом очищается её сохранённый базовый тип.

Комбинация пары начинается на уже переставленном поле. Центр — клетка назначения. Для молнии целевой тип задаёт партнёр. Молния+ракета превращает все остальные фишки целевого типа в ракеты, чередуя H/V по чётности индекса. Молния+бомба аналогично превращает их в бомбы. Партнёр пары срабатывает своим эффектом, обе исходные specials считаются активированными один раз. Прочие затронутые specials продолжают цепную реакцию.

Бомба — квадрат радиусом 2; двойная — радиус 4. Ракета+ракета — крест шириной 1; ракета+бомба — крест из 3 строк и 3 столбцов. Границы клипуются размером поля. Молния+молния очищает всё поле, затем разрешаются refill и каскады.

## Очки и транзакция

100 за фактически удалённую фишку, включая special. Новый якорь не считается удалённым. Каскадный множитель применяется к удалённым фишкам; бонусы начисляются отдельно: +200 за созданный special, +100 за активацию, +500 за комбинацию пары. Множитель начинается с ×1, шаг .25, максимум ×3. Все значения конфигурируются.

Game разрешает весь ход на копии поля и RNG. Board/score/stats публикуются только после успеха и проверки безопасного диапазона целых чисел. При превышении бюджета/переполнении всё откатывается. Shuffle сохраняет special в той же клетке и перемешивает только обычные фишки. Невозможная перестановка приводит к явной ограниченной по времени ошибке.

## События и browser layer

События: swap, special-created, special-activated, combo, transform, clear, gravity, spawn, shuffle. У каждого — самостоятельный снимок поля; для воздействия есть список targets. Количество очков волны находится в clear.points, включая бонусы.

Core синхронен. Renderer блокирует пользовательский ввод, пока последовательно воспроизводит события. Состояние анимаций не записывается в game-core и не расходует его RNG. requestAnimationFrame использует ограниченную дельту и не накапливает время в скрытой вкладке. Падение сопоставляет сохранённый порядок фишек по столбцам.

Canvas 2D используется только для стенда. Фигуры и частицы рисуются локально; размер framebuffer ограничен DPR 2. Reduced Motion отключает тряску, вспышки, частицы и пространственные переходы. AudioService создаёт короткие оригинальные тоны Web Audio, ограничивает число голосов и не запускает AudioContext до действия пользователя. Музыки ещё нет.

## Save / replay

Save v2, rules `mvp2-v1`. Миграция v1 сохраняет исходное поле, seed, rngState, score и статистику, добавляет defaults specials и нулевые новые счётчики. Старый объект не мутируется. Продолжение идёт по новым правилам; это миграция локального прогресса, не обещание эквивалентности будущих ходов MVP-1.

Replay должен получать доверенные seed/config/limit и точную версию правил с сервера. Изменённые лабораторные fixture-поля не следует считать стартом рейтингового replay. HTTP schema validation, auth, владение сессией, срок действия, rate limiting и одноразовая запись результата относятся к backend-этапу.

## Детерминизм

Mulberry32 и uint32 seed сохранены. Никакого Math.random или времени в core. Board generation — сверху построчно; match search — горизонтали, затем вертикали; refill — снизу вверх, слева направо; shuffle — Fisher–Yates. План создания и очереди эффектов используют фиксированный порядок. Анимации и SFX не влияют на результат.


## MVP-3: клиент и хранение

`src/app/main.ts` управляет экранами menu/game/result, нативными dialog, вводом и проигрыванием BoardEvent. Core не импортирует клиент. `BoardRenderer` сохраняет API MVP-2 и добавляет paused, symbols, economical. `MusicService` создаёт собственную Web Audio петлю.

`StorageService` изолирует доступ к хранилищу, валидирует настройки и вызывает `Game.restore` для проверки сохранения. Обёртка профиля version=1 содержит прежний core Save v2, поэтому миграция v1 → v2 продолжает работать. Best отделён от текущей партии. Ошибки JSON, неизвестные версии, повреждённые доски и квоты не препятствуют запуску игры; показывается предупреждение.

Core.swap синхронно получает конечную доску. Сразу сохраняется именно она, затем клиент показывает события. Busy блокирует вторые ходы; paused замораживает renderer. Во время замороженной последовательности запрещена замена партии и выход в меню, чтобы старые события не попали в новую игру. После возобновления эти кнопки доступны по окончании событий.

RU/EN строки размещены в i18n.ts и data-t атрибутах HTML. Статистика и числа форматируются по текущей локали. localStorage — первый адаптер; переход на IndexedDB и миграции прогресса запланированы на MVP-6. Phaser/Vite ещё не подключены.
